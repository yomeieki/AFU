# 结算页餐具选择（同城外送 + 到店自取）设计

日期：2026-09-14　作者：Claude（00 规划）　状态：待店主审阅

## 0. 一句话

同城外送和到店自取的结算页多一行「餐具」，顾客必须选「无需餐具」或「需要餐具」，需要时再选「商家按餐量提供」或指定 1–10 份；免费；记住顾客上一次的选择。选择存在订单的独立字段里，不再拼进备注，小票两联、工作台、订单详情都单独显示一行。

## 1. 已拍板的产品决策（改动需重新确认）

| # | 决策 | 结论 |
|---|---|---|
| T1 | 渠道 | 同城外送、到店自取都有；全国邮寄没有 |
| T2 | 是否必选 | **必选**（店主 2026-09-14 选 A）。没选时提交按钮显示「请选择餐具」，点它弹出选择 |
| T3 | 选项 | 「无需餐具」（下方绿色小字「环保助力」）/「需要餐具」→ 数量二选一：「商家按餐量提供」（默认）或指定份数 |
| T4 | 份数上限 | 1–10 份（店主定） |
| T5 | 收费 | 免费（店主定）。任何金额明细里都**不出现**餐具行，不写「¥0」 |
| T6 | 记住选择 | 记住（店主定）。按**顾客**记，取该顾客最近一张有餐具记录的同城/自取单；预填后视为已选，行上直接显示当前值，顾客可改；从没选过的顾客才看到「请选择」 |
| T7 | 存储 | 订单独立字段，不进备注。备注恢复成纯备注，20 字全留给顾客 |
| T8 | 老订单 | 不回填。老单没有餐具字段，各处不显示餐具行（老外送单备注里的「[需要餐具]」原样留着） |
| T9 | 旧版小程序 | 服务端**永远不强制**这个字段（小程序没有强制更新机制，旧版本会一直在）。旧版外送页发来的备注前缀「[需要餐具] 」由服务端剥掉，并记为「需要餐具 · 按餐量」 |
| T10 | 骑手备注 | 发给运力方的备注只带顾客备注，不带餐具（餐具在店里装袋时就放好了） |

本 spec 推翻 `2026-09-11-local-pickup-design.md` §5.4 第 7 条「备注（20 字，无「需要餐具」）」：自取也要选餐具。
本 spec 收口 `2026-09-03-local-delivery-design.md` 列为二期的「精细餐具选项」与小票「餐具标记」。

## 2. 对标

- **美团外卖结算页**（店主 2026-09-14 截图）：「餐具」行未选时橙色「请选择」；弹层两个大按钮「需要餐具 / 无需餐具（助力环保）」；选需要后「商家按餐量提供」或份数步进器；可按地址记住。
- 我们的差异：按**顾客**记而不是按地址（自取没有地址，按顾客两个渠道一致）；不做「后续该地址下单都需要餐具」开关，直接记最近一次；文案用店主定的「环保助力」。

## 3. 数据模型

### 3.1 订单表 `orders` 加 2 列

| 列 | 类型 | 含义 |
|---|---|---|
| `tableware_mode` | `VARCHAR(16) NULL` | `NONE` 无需 / `BY_MEAL` 按餐量 / `COUNT` 指定份数；null = 未记录（邮寄单、老订单） |
| `tableware_count` | `INT NULL` | 仅 `COUNT` 时为 1–10，其余为 null |

一次 Prisma 迁移 `20260917000000_order_tableware`，两列可空，老数据零影响，不回填。

### 3.2 统一文案（三端同一套）

| mode | 小票 | 工作台 / 后台 / 小程序 |
|---|---|---|
| `NONE` | 无需餐具 | 无需餐具 |
| `BY_MEAL` | 餐具：按餐量 | 需要餐具 · 按餐量 |
| `COUNT` | 餐具：N 份 | 需要餐具 · N 份 |
| null | 不印 | 不显示 |

服务端 `services/tableware.ts` 与小程序 `utils/tableware.js`（ES5）各一份文案函数，单测锁同一组输出。

## 4. 服务端

### 4.1 下单 `POST /api/orders`

- body 新增可选 `tableware: { mode: 'NONE' | 'BY_MEAL' | 'COUNT', count?: number }`。
- 校验（40001）：`mode` 只能是三者之一；`COUNT` 时 `count` 必须是 1–10 的整数；非 `COUNT` 时不得带 `count`。校验以追加的独立 `refine` 实现，排在现有地址/时段/取餐人校验之后，不改动它们的报错文案。
- `LOCAL` / `PICKUP`：有就写入两列；没有就写 null，**不拒单**（T9）。
- `EXPRESS`：忽略该字段，两列写 null。
- 写入位置：共用的 `tx.order.create` 里 `remark` 旁边。

### 4.2 旧版小程序兼容（T9）

- 在备注 20 字校验**之前**做预处理：备注以「[需要餐具]」开头（后面空格可有可无）时剥掉这个前缀；若同一请求没有 `tableware`，记为 `{ mode: 'BY_MEAL' }`。
- 效果：旧版顾客「打开需要餐具 + 备注写 14 字以上」现在会被 20 字限制拦下报错，发版后可以正常下单；新订单的备注里不再出现这个前缀。

### 4.3 记住上次选择

- 新接口 `GET /api/orders/tableware-last`（需登录）：取该顾客 `deliveryType ∈ {LOCAL, PICKUP}` 且 `tableware_mode` 不为空的最近一张单，返回 `{ mode, count }`，没有则返回 null。
- 必须注册在 `GET /api/orders/:id` 之前（同 `pickup-contact`）。
- 邮寄单、旧版客户端下的无记录单不会覆盖上一次的选择。

### 4.4 响应

- 下单响应 `orderCreatedView` 加 `tablewareMode` / `tablewareCount`（幂等重放走同一个函数，结果一致）。
- 顾客订单列表与详情：整行下发，自动带上。
- 后台订单列表 `orderListSelect` 显式加两列；后台详情自动带上。
- 工作台快照卡片 `toCard` 加 `tableware: { mode, count } | null`，`note` 仍只放顾客备注。

### 4.5 小票（`services/ticket/content.ts`）

- 取餐联/配送联：在收件信息块之后、备注块之前单独一行加粗「无需餐具」/「餐具：按餐量」/「餐具：N 份」。
- 厨房联：紧跟「尾号」那一行之后印同一行（装袋的人第一眼要看到）。
- 这一行放在独立数组里，**不受**票面超长时「压缩备注」那一步影响，永不截断。
- `ticket/index.ts` 的类型、查询字段、`toTicketInput` 三处都加两列；删掉 `content.ts` 里「餐具标记目前无字段」的过期注释。
- 邮寄票不印。

### 4.6 不改的地方

- 运力方下单备注（`delivery/orchestrator.ts`）：仍只传顾客备注（T10）。
- 企微新订单推送：不加（现在也不推备注）。
- 退款、统计、积分：与餐具无关。

## 5. 小程序

### 5.1 结算页（外送 `pages/local/confirm`、自取 `pages/local/pickup`）

- 备注卡片里、「备注」上方加一行「餐具」：未选时右侧橙色「请选择 ›」，已选时显示 §3.2 文案 + `›`，整行可点。
- 外送页删掉原来的「需要餐具」开关、`needTableware` 状态和备注前缀拼接；两页提交的备注都只取顾客输入、截到 20 字。

### 5.2 选择弹层（两页同款）

- 标题「是否需要餐具」，右上「关闭」。
- 两个并排大按钮：「需要餐具」/「无需餐具」，后者下方绿色小字「环保助力」；选中态品牌色描边 + 浅底。
- 选「需要餐具」后下方出现「餐具数量」：左边「商家按餐量提供」（默认选中），右边「− N 份 +」步进器，范围 1–10，点步进器即切到指定份数（首次为 1 份）。
- 底部「确定」：没选需要/无需时置灰；确定后关闭弹层并更新行和按钮状态。关闭而不确定 = 保持原选择。

### 5.3 提交按钮状态

- 新状态文案「请选择餐具」，按钮**可点**，点击打开弹层（不是灰掉不响应）。
- 外送页优先级：放在地址、定位、运费计算中、运费失败、阻塞原因、报价无效/过期**之后**，优惠加载中、提交中**之前**。
- 自取页优先级：放在阻塞原因、没选时段、时段过期、手机号无效、未达起送、金额未就绪**之后**，优惠加载中、提交中**之前**。
- 两页提交函数的守卫都要拦住「没选餐具」。

### 5.4 预填

- 两页进入时静默请求 `tableware-last`；返回有值且顾客此刻还没自己选过，才预填。请求失败 = 保持「请选择」，不提示。

### 5.5 订单详情 `pages/order/detail`

- 「备注」行下方加「餐具」行，文案同 §3.2；邮寄单和老订单不显示。

### 5.6 预览台

- `local-confirm.html`、`local-pickup.html` 换成「餐具」行；新增一张「餐具选择弹层」镜像（需要餐具 + 指定 2 份的状态）。

## 9. 上线顺序

1. 先部署服务端（旧版小程序立刻受益于 §4.2，不再因前缀超长下单失败）。
2. 再从主仓上传小程序体验版、提审。反过来的话，新版小程序发来的 `tableware` 会被旧服务端丢掉。

## 10. 手工验收

1. 新顾客进外送结算页，餐具行「请选择」，提交按钮「请选择餐具」，点按钮弹层；选「无需餐具」确定后可提交。
2. 再下一单，餐具行直接显示「无需餐具」；改成「需要餐具 · 3 份」提交。
3. 自取结算页同样必选，并预填上一次「需要餐具 · 3 份」。
4. 小票取餐联和厨房联都有「餐具：3 份」；工作台卡片、抽屉、订单详情、同城订单列表都显示；金额明细里没有餐具行。
5. 邮寄下单没有餐具行，小票没有。

## 勘误

- **2026-09-14 实施期间（Task 4）**：§5.3 自取页优先级原文把「金额未就绪」放在「未达起送」之后单独一段，与「餐具排在其后」的顺序矛盾——`amountState='ready'` 是餐具判定要读的信号，必须等金额已经算出来才有意义，所以「金额未就绪」必须先于餐具判定，即先于「优惠加载中」。已改为「……未达起送、金额未就绪之后，优惠加载中、提交中之前」，与 `apps/miniapp/utils/pickup-checkout-state.js` 的实现一致。
