# 分类内商品排序（后台可拖拽 / 按销量自动）设计

日期：2026-09-17　作者：Claude（00 规划前置设计）　状态：待店主审阅

## 0. 一句话

后台给**每个分类**单独设「排序方式」：手动（拖拽排）或按近 30 天销量自动排；顾客端分类页该分类那一段就按这个顺序显示。

## 1. 已拍板的产品决策（改动需重新确认）

| # | 决策 | 结论 |
|---|---|---|
| S1 | 粒度 | **每个分类各自设**（店主 2026-09-17 定）。凉菜可以按销量、特色菜可以手动 |
| S2 | 两种方式 | `MANUAL` 手动拖拽 / `SALES_30D` 按近 30 天销量从高到低 |
| S3 | 销量口径 | 近 30 天**已付款**订单里该商品的件数，复用现有「真实订单」口径（`REAL_ORDERS`，自动排除测试单），不含赠品行。**按付款时间计，事后退款/取消不扣回**——与后台热销榜完全同一口径，两处数字必须对得上 |
| S4 | 手动怎么排 | 后台拖拽；另配「上移 / 下移」按钮，手机上打开后台时用 |
| S5 | 默认 | 新装/存量一律 `MANUAL`，初始顺序 = 现在的顺序（按录入先后），所以**上线当天顾客端看到的顺序不变** |
| S6 | 新加的菜 | 手动模式下排到本分类**最后**；销量模式下没有销量自然排最后 |
| S7 | 推荐置顶 | 不变。勾了「推荐」的菜在整个列表最前（首页取前 6 靠它），分类段内其余按本方案的顺序 |
| S8 | 顾客端 | 不用改小程序也能生效——顺序由服务端排好（见 §4）。小程序那一批（分类联动）照常另走提审 |

## 2. 对标

- **美团 / 饿了么商家后台**：菜品可在分类内拖拽排序，也可切「销量优先」自动排；两者按分类分别设。
- **点单型小程序（瑞幸、蜜雪）**：菜单顺序人工固定，热销单独成组置顶。
- 我们的差异：不做「热销」独立分组（店里已有「推荐」置顶），把销量排序做成分类级开关。
- 说明：形态层面的一般观察，未逐一截图比对。

## 3. 数据模型

### 3.1 两处加列（一次迁移）

| 表.列 | 类型 | 含义 |
|---|---|---|
| `products.sort_order` | `INT NOT NULL DEFAULT 0` | 手动排序值，同分类内从小到大。存量全为 0，靠 `created_at` 兜底＝现状顺序 |
| `categories.product_sort_mode` | `VARCHAR(16) NOT NULL DEFAULT 'MANUAL'` | `MANUAL` / `SALES_30D` |

零风险迁移：两列都有默认值，不回填，老数据行为不变（S5）。

### 3.2 近 30 天销量

聚合 `order_items`：`isGift = false`、`productId` 非空、所属订单已付款且 `paidAt >= now - 30d`，并 spread `REAL_ORDERS`；`groupBy productId` 求 `sum(quantity)`。

- 与后台热销榜同一套写法（`routes/admin/stats/overview.ts` 的 hot 聚合）。
- **只缓存这份销量聚合 60 秒**（写法照 `services/local-settings.ts`），**不缓存商品列表本身**——整份列表若缓存，上下架、一键收档、改库存、下单扣库存都会在顾客端滞后最多 60 秒。后台改排序方式或拖拽保存后主动清这份缓存。

## 4. 服务端

### 4.1 公开列表 `GET /api/products`

现在的排序是纯数据库 `orderBy`。改为：**取出该渠道全部上架商品 → 在内存里排序 → 再分页**。

排序规则：

1. `isRecommended` 降序（首页取前 6 靠它，S7）
2. 分类的 `sortOrder` 升序，相同再按 `categoryId` 升序
3. 分类内：`MANUAL` → `sort_order` 升序，相同按 `created_at` 升序；`SALES_30D` → 近 30 天销量降序，相同按 `sort_order`、`created_at` 升序
4. 最后一律 `id` 升序兜底，保证分页稳定

为什么放内存：不同分类要用不同规则，SQL 一条 `ORDER BY` 表达不了。数据量小——同城 121 道、邮寄 19 道（2026-09-17 实测），整表取回 + 排序的成本远小于一次网络往返。列表本身不加缓存（见 §3.2），只有销量聚合走缓存。

`select` 同时补两个字段：`categoryId`（分类联动那一批要用）、`sortOrder`（后台排序界面要用）。

### 4.2 后台接口

| 接口 | 作用 |
|---|---|
| `PUT /api/admin/categories/:id` | body 允许 `productSortMode`，值域 `MANUAL` / `SALES_30D`；改完清列表缓存 |
| `POST /api/admin/categories/:id/product-order` | body `{ ids: number[] }`，按数组下标写 `sort_order = index`；校验：ids 必须正好是该分类下所有未删除商品（多、少、重复、跨分类一律 40001），事务内批量更新；改完清缓存 |
| `GET /api/admin/products?categoryId=` | 返回顺序与顾客端一致（同 §4.1 规则），并返回 `sortOrder` 与 `sales30d`，供后台界面显示 |

新建商品时 `sort_order` 取该分类当前最大值 +1（S6）。**把已有商品改到另一个分类时同样取新分类的最大值 +1**——否则它带着旧的排序值过去，可能直接跳到新分类第一位。

## 5. 后台界面

商品管理页在按分类筛选时，工具条上多一块：

- **排序方式**下拉：手动排序 / 按近 30 天销量。切到销量时，列表按销量排好并显示每道菜的 30 天销量，拖拽把手禁用并提示「当前按销量自动排序，如需手动请切回手动排序」。
- **手动模式**：每行左侧一个拖拽把手，拖动即调顺序；行尾「↑ / ↓」按钮做触屏兜底。松手/点按钮后**立即保存**（调 §4.2 的接口），失败时回滚到拖动前的顺序并提示。
- 排序控件只在「选定了某个分类、且没有关键词搜索、状态筛选为全部」时启用——只要列表不是该分类的全集，拖拽保存就会被服务端判为非法（§4.2 要求 ids 是全集）。后台该分类商品超过 200 道时禁用拖拽并提示（一页取不完）。

拖拽用浏览器原生 `draggable` 事件实现，不引第三方库。

## 6. 验收

### A. 可脚本化

| 命令 | 期望 |
|---|---|
| `npx tsc --noEmit -p apps/server/tsconfig.json` && `npm run build:admin` | 通过 |
| `npm test --workspace=apps/admin` | 全绿 |
| 服务端自检脚本 `apps/server/scripts/selftest-product-sort.ts`（`apps/server` 没有单测框架，惯例是 selftest 脚本）：推荐置顶、分类顺序、手动/销量两种模式、并列时的兜底、分页切片稳定 | 全绿 |
| 后台单测放 `apps/admin/src/utils/`（`npm test --workspace=apps/admin` 只扫 `src/*.test.ts` 与 `src/utils/*.test.ts`） | 全绿 |
| `curl '…/api/products?channel=LOCAL&pageSize=1' \| grep -o categoryId` | 有 `categoryId` |

### B. 手工（后台 + 小程序）

1. 后台选「阿福凉菜」→ 排序方式「手动」→ 把某道菜拖到第一 → 刷新页面顺序保持 → 小程序分类页该分类第一道就是它（推荐菜仍在最前）。
2. 切「按近 30 天销量」→ 列表按销量重排并显示销量数字 → 小程序端 60 秒内跟着变。
3. 在该分类下新建一道菜 → 手动模式下出现在本分类最后。
4. 另一个分类仍是手动，互不影响。
5. 「全部分类」视图下没有排序控件。
6. 拖拽保存失败（断网）时顺序回滚并提示。

## 7. 风险与预案

| 风险 | 预案 |
|---|---|
| 内存排序拖慢接口 | 商品量小 + 60 秒缓存；单测锁定排序纯函数；若日后单渠道超 500 道，改为落库的物化排序值 |
| 拖拽保存与并发编辑打架 | 保存接口要求 ids 是该分类的全集，不匹配直接报错，店主刷新后重排 |
| 店主切到销量模式后以为手动顺序丢了 | 手动顺序仍存在库里，切回来即恢复；界面文案写明 |
| 缓存导致「后台改了小程序没变」 | 后台写操作主动清缓存；文案说明最多 60 秒 |
| 销量口径误解（含取消单？） | 只算已付款且未被标记为测试的订单；取消/退款的单不在内（与后台热销榜一致） |
