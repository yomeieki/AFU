# 会员 M5：真机联调、文档同步与收尾 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务执行本计划。步骤用 checkbox（`- [ ]`）语法追踪。
> **前置**：M1–M4 已全部合入 main **并部署到生产**（会员代码走的是与同城完全相同的上线路径：合并 → `scripts/deploy.sh` → `prisma migrate deploy` → 后台配置 → 上传体验版）。本计划**只写 M5**：真机一分钱级别的全链路联调、四份文档同步、提审前检查项、收尾清理。**不新增任何顾客端与后台功能。**
> **本文档性质**：规划文档，由 Principal Engineer 角色撰写，本身不修改任何 `apps/` 代码。联调中发现的阻断性 bug 另开小分支修，保持本计划的证据链干净（沿用同城 M4 计划的做法）。

设计依据：spec §8 M5、§9（真机走全链路）、§10（风险：店员按原价退、顾客投诉退款不退券、审核要求规则公示）；masterplan 「本次要产出的文档」第 5 条与「落盘时未做的事」（`docs/requirement.md:142,148`）；`docs/ops-test-orders.md`（生产库测试单的隔离流程）；`docs/superpowers/plans/2026-09-04-local-delivery-m4-device-integration.md`（体例与真机联调的写法）。

**Goal:** 在真机、真实微信支付、真实生产库上把「发券 → 用券下单 → 随单赠品 → 订单完成得分 → 部分退款扣回积分且不退券 → 未支付取消释放 → 换券 → 领券」整条链走通一次并留下证据（截图 + 后台记录 + 库表快照）；把 `docs/staff-guide.md`、`docs/api.md`、`docs/requirement.md`、`docs/miniapp-release-checklist.md`、`docs/database.md` 同步到「会员功能已上线」状态，其中店员手册必须有「退款不退券」的统一话术；把联调留下的测试单、测试模板、测试赠品、测试商品按 `docs/ops-test-orders.md` 隔离干净；产出提审所需的补充说明文案。做完 M5，店主拿着这些证据可以自己决定提审。

**Non-goals（详见文末《明确不做》）：** 不做任何新功能；不做 spec §12 二期项；不在联调分支修 bug；不代替 PO 在生产填任何密钥或做提审点击；不接打印机（票面优惠行的渲染在 M2 Task 9 已改，真机打印核对以打印机上线为准）。

## Global Constraints

- **真实资金**：本计划涉及真实微信支付。每一步先确认前一步的订单状态再继续；全部测试单联调后**必须**退款到 0 并打 `isTest` 标（`PATCH /admin/orders/:id/test-flag`）；总预算见 D1。
- **测试数据隔离**按 `docs/ops-test-orders.md` 三步走：专用测试商品（名带「【内部联调】」）→ 联调后软删除 → 订单打 `isTest`。本计划**新增两类**测试数据也要隔离：测试券模板（名带「【内部联调】」，联调后置 OFF）、测试赠品（联调后删除）。
- **`isTest` 单不发积分**（spec §5.4）——所以联调时**先跑完得分/扣回验证再打标**，打标后 `settleMissedPoints` 不会再碰它。顺序错了得分步骤永远验不到。
- 文档里**不出现任何密钥、商户号、openid**；截图打码手机号。
- 每个文档任务的 Done 判据都包含「与联调记录里的实际文案/字段一致」——文档不是照 spec 抄，是照跑出来的结果写。
- 提交信息中文、`type(scope): 摘要`；文档改动与联调记录分开提交。

### Task 2: 真机全链路联调（核心任务）

- [ ] **Step 1: 赔偿券发放 → 顾客端可见**
  后台用户页 → 找到联调账号 → 「发券」T1，备注「联调」，关联订单留空 → 二次确认 → 手机「我的」页头券数 +1、「我的券」可用 Tab 有该券、券码与后台「券记录」一致、`issuedBy` 是登录名。
- [ ] **Step 2: 用券下单（一分钱）**
  商品 A ×1（¥0.02）→ 结算页优惠组件自动选中 T1（D2 默认）→ 合计 ¥0.01 → 提交 → 微信支付页金额 **¥0.01** → 支付 → 后台订单列表展开区显示「优惠券 −¥0.01」、退款弹窗第一步灰字「实付 ¥0.01（商品 ¥0.02 − 券 ¥0.01）」（不真退）→ 工作台详情抽屉金额明细同样 → 企微/PushPlus 推送含「已用券 −¥0.01」。
- [ ] **Step 3: 得分链路（需 ≥ ¥2.00 的实付，见 D1）**
  商品 B ×1（¥2.00）无券 → 支付 → 后台接单 → 发货（快递单号随便填）→ 手机确认收货 → **2 分钟内**「我的」积分 +2（钩子）或最迟 3 分钟（兜底任务）→ 积分明细有「消费得分 +2，有效期至 …」→ 后台用户页积分列 +2 → 订单详情「本单获得 2 积分」。
- [ ] **Step 4: 随单赠品**
  商品 A ×1 + 结算页赠品 G1 ×1（扣 1 分）→ 合计 ¥0.02 → 支付 → 订单详情商品行有「赠」标与「积分 1 × 1」→ 后台展开区赠品行 → 工作台商品清单「赠·」前缀 → 商品 A 库存 −2（付费 1 + 赠品 1）→ `points_goods.issued_count = 1` → 积分明细「随单赠品 −1」。
- [ ] **Step 5: 部分退款扣回 + 不退券**
  对 Step 3 的 ¥2.00 单后台部分退 ¥1.00 → 退款到账推送 → 积分 −1（`REFUND_DEDUCT`）→ 再对 Step 2 的用券单全额退 ¥0.01 → 订单「已退款」、**券仍是「已用」**（顾客端「我的券 → 已用」Tab；后台券记录 status USED）→ 订单详情显示「退款不退回优惠券与积分」灰字。
- [ ] **Step 6: 未支付取消释放**
  商品 A ×1 + T3（先在领券中心领一张，顺便验 Step 7 的一半）+ 赠品 G1 ×1 → 提交**不支付** → 订单详情「取消订单」→ 券回「可用」Tab、积分 +1（`GIFT_REVERT`）、商品 A 库存回、`issued_count` 回落。再下一单同样配置不支付，**等 15 分钟**看超时任务做同样的事（这一步可与 Step 7/8 并行等）。
- [ ] **Step 7: 换券与领券**
  积分商城 → T2 用 1 分兑换 → 「我的券」多一张、积分 −1、积分明细「兑换券 −1」；领券中心 → T3 第二次领取 → 「已达上限」toast；后台券模板 T3 `issuedCount` 与「发放记录」一致。
- [ ] **Step 8: 同城用券（P7 满足时）**
  同城商品 C ×1 + 一张 `channel=ALL` 或 `LOCAL` 的券 → 报价 → 合计 = 小计 − 券 + 运费 → 支付 → 工作台同城列卡片与抽屉显示优惠 → 后台取消配送/退款流程按同城既有方式收口。**P7 不满足则标「未验」**，不伪造。
- [ ] **Step 9: 越权与降级（手机上能做的）**
  飞行模式下打开结算页 → 优惠组件显示「暂不可用」且仍可提交（恢复网络后再提交）；未登录微信号（若有 D2 的第二个号）打开封面 → 点会员中心 → 显示登录占位而非白屏。
