### 1.4 签名方案
```
sig = sha1(USER + UKEY + stime)   // 40 位小写十六进制字符串
```
`stime` 为 10 位 Unix 时间戳（秒）。**[已确认]**

每次请求的公共参数：`user`、`stime`、`sig`、`apiname`（接口名）、可选 `debug=1`（非 JSON 格式方便调试）。**[已确认]**

### 1.7 语音播报（云喇叭/真人语音款打印机专属）
- 飞鹅支持"来单播报"的打印机型号（型号名通常带 "语音" 或 "-Y" 后缀），默认在打印新订单时自动播报固定语音"您有新的订单"，无需额外参数，只要走 `Open_printMsg` 打印即触发 **[推断，来自第三方博客与产品页整合，未见官方 API 文档逐字给出触发条件]**
- 可用专用指令控制播报内容/场景，检索到的用户整理版本包含：
  - `<AUDIO-REFUND>`：播报"有用户申请退单了"
  - `<AUDIO-CANCEL>`：播报"有用户申请取消订单了"
  **[推断/待核实 —— 这两个标签来自第三方检索摘要而非官方文档原文抓取，接入前务必在 apidoc-cn.html 原文里核实标签拼写与是否需要打印机支持"云喇叭"型号]**
- 结论：语音播报强依赖硬件型号（需选购带"真人语音"/云喇叭功能的机型），软件侧多数情况下**只需正常调用 `Open_printMsg` 打印一张新订单小票，播报是打印机固件自动触发的**，不是一个独立的"播报 API"。这点与芯烨云"显式调用播放语音接口"的模式不同（见下）。

### 1.8 打印状态回调（backurl）
- 触发条件：`Open_printMsg` 执行后，打印机真正打印完成时，飞鹅服务器会 POST 回调到开发者预先在**后台配置**的回调地址（文档抓取未明确回调地址是在开发者后台哪个页面配置，需要登录后台核实，大概率在"账号设置"或"开发者信息"里有"回调地址"字段）**[推断需核实]**
- 回调参数（POST，`application/x-www-form-urlencoded`）：
  - `orderId`：打印时返回的订单标识
  - `status`：订单状态，`1` 表示打印成功
  - `stime`：状态变更的 Unix 时间戳
  - `sign`：数字签名（用于校验回调合法性，签名算法/公钥需在文档里进一步核实，抓取摘要提到"RSA SHA256"但未给出具体公钥，**[推断，需核实]**）
- 商户服务端必须在 5 秒内返回字符串 `"SUCCESS"`，否则飞鹅会重试推送 **[推断/来自摘要，需核实重试次数与间隔]**

### 1.9 频率限制 / 幂等
- 官方文档抓取未见明确"每台打印机每分钟条数限制"的说明 **[未查到，需核实——建议直接询问飞鹅商务或在文档搜索"限流""频率"关键字]**

### 2.6 语音播报（芯烨云明显比飞鹅更"API 化"）
- `/playVoice` 是显式的语音播报触发接口，与打印动作解耦，可以单独调用（例如"新订单来了但小票还没打印完就先喊一声"）**[已确认存在该接口，参数细节如下为抓取摘要]**
- 关键参数：
  - `payType`：支付方式（`41`=支付宝，`42`=微信，`43~55`=其它支付方式）
  - `payMode`：播报场景（`59`=退款，`60`=收款/到账，`61`=消费）
  - `money`：金额，最多两位小数
  **[推断/待核实——这是抓取摘要中给出的枚举值，具体数值需在 PDF 原文核对，不同文档版本可能有出入]**
- `/setVoiceType` 可配置声音风格（如男声/女声/播报模板），具体可选值需查 PDF **[推断，需核实]**
- 结论：如果只是想在"顾客下单支付成功后播报'您有新的订单'"，更贴近飞鹅那种"打印即自动播报"的模式；如果想要"播报具体金额/支付方式"这种更精细的场景，芯烨云的 `/playVoice` 显式接口更灵活，但其参数枚举语义（41/42/59/60/61…）偏向"收银台已收款播报"场景，不完全等价于"外卖新订单播报"，需要在真实沙盘/测试机上验证是否能定制成"您有新的外卖订单"这句话，还是只能播报固定模板 **[推断，需核实]**

## 六、给自贡凉菜店的选型建议

**推荐：飞鹅云打印为首选，芯烨云 XPYUN 为备选/双活方案，不建议易联云、佳博/365 作为首选。**

理由：

1. **接入简单度**：飞鹅和芯烨都是"开发者账号 + sha1 签名"的轻量模式，几十行 Node.js 代码就能封装（Express 里做一个 `printerClient.printOrder(sn, content)` 的工具函数，签名用 Node 内置 `crypto` 模块的 `sha1` 即可，无需额外依赖）。易联云的 OAuth2.0 + token 刷新频率限制（20次/天，需要持久化 token）对一个单店小系统来说是不必要的复杂度。

2. **语音播报**：这是本方案的硬需求之一（顾客下单支付成功要"喊一声"）。
   - 芯烨云有**明确、独立的 `/playVoice` API**，语义上更贴近"程序主动触发播报"这个需求，工程上更可控、更容易测试，**但其参数枚举（41/42/59/60/61 等）更偏收银场景，能否播报"您有新的外卖订单"这句自定义文案还需要实测确认**。
   - 飞鹅的语音播报更像是"硬件自带的固定行为"（买真人语音款机型，打印时自动喊单），软件侧几乎不用管，**但灵活性差**，如果想自定义播报文案或做"离线告警时也喊一声"这种额外场景，飞鹅可能做不到（除非它也有类似 `<AUDIO-XXX>` 标签，这块本报告标为待核实）。
   - **建议**：如果"语音播报的文案/触发时机需要灵活控制"（比如想在下单播报之外，也做"打印机离线告警"的语音提示），优先选芯烨云，先用真实测试打印机验证 `/playVoice` 到底能不能播自定义文案；如果"只要有个大概的'来单提醒'声音就行，不追求定制文案"，飞鹅的真人语音款机型更省心。

3. **订单去重（避免重复打印）**：芯烨云原生支持 idempotent token，这是一个明显加分项——外卖/收单场景经常有支付回调重复推送的问题，有官方幂等支持能省很多自己维护去重表的工作量。飞鹅则需要业务方自己在 Express 里对"订单号是否已打印过"做判断（比如用一张 `printed_orders` 表或 Redis `SETNX` 做去重锁），实现不难但要记得做，否则容易出现顾客付款网络抖动导致同一单打印两次的问题。

4. **离线检测告警**（本方案第三个硬需求）：两家都提供 `queryPrinterStatus`/`queryPrintersStatus` 接口可以轮询打印机在线状态，工程上做法一致：Express 后端起一个定时任务（`node-cron` 之类），每隔几分钟调一次"查询打印机状态"接口，如果连续几次都是离线，就通过已有的 PushPlus 通道（该项目已经在用，参见 memory 中"通道自检脚本"）推送告警给店员。这块两家能力相当，不构成选型决定因素。

5. **网络制式**：如果凉菜店打印机放在收银台附近，WiFi 信号稳定，选 WiFi 款即可，成本最低；如果打印机离路由器较远或者店里网络不稳，建议直接买"WiFi+4G 双模"机型，4G 作为兜底，这两家都有对应型号。芯烨云支持电信卡（飞鹅的 GPRS 老款不支持电信），如果店里主力用的是电信卡，芯烨云机型选择面更宽。

6. **落地建议（工程角度）**：
   - 由于飞鹅的回调签名细节、语音自定义标签、限流数字，芯烨云的 `/playVoice` 具体可用文案，易联云的完整 base URL 和签名算法，本次调研都未能 100% 从官方原文确认，**正式开发前建议先各自注册一个开发者测试账号（免费），拿一台真实打印机跑通"打印一张小票 + 触发一次语音"的最小闭环**，再决定最终采购哪家、买几台。
   - 建议 Node.js 侧统一封装成一个 `printerAdapter` 接口（`bindPrinter`、`printTicket(content)`、`queryStatus`、`triggerVoice`），底层实现切换飞鹅/芯烨互不影响业务代码，方便万一某天打印机厂商服务不稳定时切换厂商或做双通道容灾（比如打印走飞鹅、语音走芯烨云的 `/playVoice`，虽然听起来奇怪，但技术上是可行的——两家 API 互相独立）。
