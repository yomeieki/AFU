# 接单工作台 界面规格 v1

> 可交互原型：https://claude.ai/code/artifact/ea2da1e2-450f-470b-9bf0-592d6035d7d3
> 店主 2026-09-03 定稿。**v1 先按此实现，上线试用后发现问题再改**。
> 对应方案 §7b（D8 运营工作台）。原型里的按钮都能点，行为即预期行为。

## 0. 这个页面要解决什么

店员在高峰期站着用（手机 / web-view 居多），要在两秒内判断「此刻该处理哪一单」。
因此：**摘要在前、明细在后；状态用形式编码而不只是文字；危险操作挡一道。**

工作台是店员的**默认落地页**，同城单与邮寄单混在同一套列里。

---

## 1. 列结构

五列，两个渠道共用同一套流程，同一格里做的事不同：

| 列 | 同城配送 | 全国邮寄 | 对应状态 |
|---|---|---|---|
| 待接单 | 顾客已付款，等接单 | 同 | `PAID` |
| 备餐中 | 做货，待呼叫骑手 | 打包，待填单号 | `PREPARING` |
| 等待配送员 | 已呼叫，等骑手到店 | 已打包，等快递揽收 | 同城 `Delivery ∈ CALLING/ACCEPTED/ARRIVING/ARRIVED`；邮寄 `PREPARING` 且已打包 |
| 配送中 | 骑手在送 | 快递在途 | `SHIPPED` |
| 已完成 | 已送达 | 已签收 | `COMPLETED` |

**异常不单开一列**：出问题的单留在它所在的列里变红（见 §5），店员扫一眼就知道该管哪张。

## 2. 排序规则（硬规则）

每列内：

1. **同城恒排在邮寄之上** —— 跨渠道硬优先，不比等待时长
2. 同渠道内，等待时长长的在上

理由：邮寄晚一小时发货无碍，同城晚十分钟菜就不能吃了。若单纯按等待时长排，一个等了半小时的邮寄单会把刚进来的同城单挤到下面，而那正是最该先看的。

原型中「待接单」列即为活例：等了 4:20 的邮寄单 #018 排在刚来 0:47 的同城单 #019 **下面**。

```js
ids.sort((a, b) => {
  const A = orders[a], B = orders[b]
  if (A.channel !== B.channel) return A.channel === 'LOCAL' ? -1 : 1
  return B.waitMinutes - A.waitMinutes
})
```

## 3. 渠道标注：三重编码，缺一不可

单靠颜色不够——余光扫过、店内灯光偏色、色觉障碍都会认错。

| 编码 | 同城配送 | 全国邮寄 |
|---|---|---|
| ① 卡片左侧 4px 色条 | `--local` | `--express` |
| ② 渠道徽章（图标 + 文字） | 电动车图标 +「同城配送」 | 包裹图标 +「全国邮寄」 |
| ② 渠道徽章（同城预约单） | 时钟图标 +「同城预约」、琥珀色底 | — |
| ③ 卡片内出现的字段 | 距离、骑手姓名/电话、预计送达 | 省市、快递公司、运单号 |

图例条常驻页面顶部，写明两个渠道各是什么。同城预约单另有一枚琥珀色徽章，图例里也列出。

### 配色（沿用 `apps/miniapp/app.wxss` 的品牌体系）

```
--local:       #e5441e   同城（品牌印章红）    深色主题 #ff7a54
--local-soft:  #fdf0ec                        深色主题 #33191180
--express:     #3b5bdb   邮寄（靛蓝，与主色隔 200° 色相）  深色主题 #8fa5ff
--express-soft:#eef1fd                        深色主题 #1a1f3d80
```

语义色（等待时长、异常）**独立于渠道色**，且置于卡片不同位置与形状，避免「红」一色二义：

```
--ok / --warn / --danger = #15803d / #a15c07 / #b3261e
```

中性色带暖偏（呼应品牌红），非纯灰：`--bg #f6f5f3`、`--surface #fff`、`--text-1 #1b1918`。
深浅两套完整 token 见原型 `<style>` 开头，直接抄。

## 4. 卡片：只放摘要

真实订单可能十几个菜，卡片列不下也**不该列**——卡片的任务是让人两秒内判断「该不该现在处理」。

**商品摘要规则**：
- ≤ 2 样：`口水鸡 ×1 · 蒜泥白肉 ×1`
- ≥ 3 样：`红油耳片、冷吃兔 等 6 样 / 8 份`（前两个菜名 + 样数 + 总份数，「等 N 样」用渠道色）

**备注**：黄色高亮块（`--note-bg` / 左侧 3px `--note-line`），置于商品行正下方，加粗。
**无备注的订单必须明写「无备注」** —— 留空则「没看见」与「没有」无法区分。

**等待时长**：卡片右上角等宽数字胶囊。`> 3:00` 转琥珀底，`> 6:00` 转红底白字。

**点商品摘要区打开详情抽屉。**

**状态条只在补充列名没说的信息时才出现。** 「备餐中」列里写「还没呼叫骑手」、「配送中」列里写「运输中」都是复述列名——
占一行却不增加任何判断依据。留下的应当是列名给不了的东西：异常（「一直没有骑手接单」）、骑手是谁与还有多久到
（「闪送 张师傅 · 3 分钟后到店」）、等的是谁（「等顺丰上门揽收」）。

**配送报价不上卡片。** 卡片只回答「该不该现在处理这一单」，多一行数字就稀释一分判断力；
价格是点了呼叫之后才需要的信息，放在呼叫弹窗与详情抽屉里（见 §6b）。

**餐具（2026-09-14 设计）**：同城/自取单在菜品摘要下方加一行餐具文案（「无需餐具」「需要餐具 · 按餐量」「需要餐具 · N 份」）；老单与邮寄单不显示这一行；不进金额明细。

## 5. 详情抽屉

桌面从右滑出 440px，看板留在左侧不丢上下文；手机全屏。

自上而下：备注（放大）→ 餐具（同城/自取单，见下）→ 状态条 → **完整商品清单** → 收货信息 → 配送员（已接单时）→ 金额明细 → 订单号与时间 → 底部操作区。

**商品清单的列宽**：数量列定宽 44px、金额列定宽 78px（够放 `¥1,298.00`），均右对齐；菜名占剩余空间并允许换行。
定宽是必须的——宽度随内容变会让每行金额起点错开，一列数字就读不成列。

**电话可直接点拨**（收货人与骑手都是）。

> ⚠️ 实现坑：抽屉内容区是纵向 flex，子元素默认 `flex-shrink:1`。内容一多不是撑开滚动而是被**挤扁**，而区块本身 `overflow:hidden`，被挤掉的行直接消失。
> 必须 `.drawer__body > * { flex: none }` + 父级 `min-height: 0`。拒单弹窗同理。

**餐具（2026-09-14 设计）**：同城/自取单在放大的备注下方加一行餐具文案，规则同 §4；老单与邮寄单不显示；不进金额明细。

## 6. 二次确认：分级，不是全都弹

**要弹**（改变订单状态或花钱）：接单、接单并呼叫、呼叫骑手、重新呼叫、加小费、自己送、填单号发货、标记已发货、拒单、退出工作台。

**不弹**：打给骑手、看进度、查物流。

> 不给这三个加确认是刻意的：它们没有后果（拨号系统本身还会再问一次），而店员一天点几十次。
> 若连它们也弹，很快会养成闭眼点「确认」的肌肉记忆——那时真正该拦的呼叫骑手、加小费也会被闭眼点过去，确认框就白做了。**确认框的效力来自稀缺。**

**弹窗内容必须写三件事**：这一步会发生什么 / 顾客会看到什么 / **花多少钱**。
花钱的操作额外给一块琥珀色提示，例：

> 会预扣配送费，实际约 ¥5–8。若之后取消已接单的骑手，可能产生约 ¥2 取消费。

**小费金额由店员定，不写死。** 弹窗里用加减步进器：默认 **¥1**（2026-09-07 店主从 ¥3 再压到
下限；理由同下，¥1 起步是「不预设锚点」的极端形式）、步长 ¥1、范围 **¥1–20**，
到边界按钮置灰；确认按钮文字跟着变（调到 ¥8 就写「加 ¥8」），点之前就知道花多少。
按钮 44px 触控尺寸——店员多半单手在手机上点。

默认取低值而非 ¥5，是不想用系统默认值把店员锚定在高位；加钱应当是有意识的动作。
旁边给区间参考，且不同阶段文案不同：

| 场景 | 参考语 |
|---|---|
| 等抢单（还没人接） | 高峰期通常 ¥3–5 就有人接；偏远或恶劣天气可能要更多。单次上限 ¥20，本单已加 ¥X，累计上限 ¥50。 |
| 骑手已接单 | 骑手已接单，加钱是让他优先跑这一单。单次上限 ¥20，本单已加 ¥X，累计上限 ¥50。 |

服务端仍按 `tip.maxPerCall` / `maxPerOrder` 校验，不信任前端传值。

> 「加小费」不叫「加小费重呼」：快递100 的 `addfee` 只是给当前这张等待中的单子加钱，
> **不重新发起呼叫、也不产生取消费**。「重新呼叫」是另一个独立动作（会产生取消费），
> 二者不能混在一个按钮里。

确认按钮跟随卡片渠道色（同城单不该弹出蓝色确认按钮）。

## 6b. 配送报价：接单时预取，呼叫时按最低价

### 为什么预取
地址在顾客下单时就已确定，所以**接单转「备餐中」的瞬间**后台就可以调 `batchPrice` 查价
（该接口**免费、不扣费**，快递100 客服 2026-09-03 确认）。
备餐那十几分钟店员不急，呼叫的那一刻他最急——把查询放在不急的时候做完。

### 保鲜：两层，不做第三层
备餐时长不固定（有的单十分钟、有的半小时），报价会过时，因此：

| 层 | 做法 |
|---|---|
| ① 定时 | 「备餐中且未呼叫」的单，每 **5 分钟**自动重查 |
| ② 手动 | 呼叫弹窗内的报价块上有刷新按钮，店员随时可点 |

超过 **5 分钟**的报价标为「已过期」并转琥珀底，提醒店员这个数字不作数。

> **不做「点击呼叫时按时长强制重查」**（店主 2026-09-03 否决）：既然定时在刷，最坏也就旧 5 分钟，
> 再加一层判断只会让点击卡顿。残留风险是高峰期涨价时弹窗数字与实扣可能差一两块——
> 联调时留意真实波动幅度，差得多再议。

### 呼叫策略
- **默认只呼报价最低的那一家**（省钱）
- **3 分钟无人接自动改为并呼六家**（保时效）

两个参数都要可配置。不加自动升级的话，最低价那家当时没运力时这单会一直干等，还得人工发现。
最低价往往就是运力最少的那家——便宜和慢经常是同一个原因。

> **2026-09-07 店主改口径：升级改为三级阶梯，本节上面那段「一次到底」已作废。**
>
> 现在是 **一家 →（3 分钟）并呼最便宜 N 家（默认 3）→（再 3 分钟）并呼全部**。
>
> **2026-09-12 再改：去掉第三级「并呼全部」，两级到头只发一次告警叫店员处理。**
> 弹窗同时从「列出全部报价逐家可选」改成只有两张卡：**普通配送**（走上面的阶梯）与
> **极速配送**（只呼闪送一对一，记 MANUAL；3 分钟没人接同样升到并呼 N 家）。
> 改的理由是余额：并呼冻结按家数放大（一家 ¥16.23／三家 ≈ ¥51.76／全部 ¥75.08），
> 一步跳到全表意味着每一次超时都按最贵那档占余额，而充值 100 元时全表只挂得下 1 单。
> 逐级加人后绝大多数单在第一级就被接走、只冻一笔。
> 「多花 3 分钟」这个顾虑仍然成立，所以留了出口：工作台弹窗里始终列出全部报价，
> 急单店员当场点闪送那一行即可（记 MANUAL，且同样会被后面两级兜住）。
> 每一级等多久由同一个 `escalateAfterMin` 控制。
> 实现见 `services/delivery/orchestrator.ts` 的 `NEXT_RUNG`。

### 弹窗里显示什么
```
呼叫骑手？
订单 #017 · 汇东新区丹桂大街 3 栋 2 单元 501 · 距门店 1.8 km

┌ 最低 ¥6.50 · 美团配送              2 分钟前  ↻ ┐
│ 美团 ¥6.50 · 顺丰同城 ¥6.80 · 达达 ¥7.00 ·     │
│ UU ¥7.20 · 蜂鸟 ¥7.80 · 闪送 ¥12.00           │
└───────────────────────────────────────────────┘

⚠ 按最低价呼叫美团配送，预扣 ¥6.50。3 分钟无人接自动改为并呼六家。

[取消]              [呼叫美团 ¥6.50]
```
确认按钮带上运力名与金额（「呼叫美团 ¥6.50」），点之前就知道叫谁、花多少。

弹窗正文以**订单号 + 地址 + 距离**为主，不再解释「向六家同步呼叫」的机制——店员天天点，不需要每次重复告知。

### 数据要求
`Delivery` 必须存**当次六家报价的快照**（含查询时间）。没有它，将来无法回答
「只呼最低价到底省了多少、值不值」，也无法验证扣费是否与报价一致。

### 联调必须验证
**「实际扣费 = 中标运力的报价」这是从文档推断的，未经证实。**
若快递100 实为统一定价，则「选最低价」整套策略失去意义。
第二步真下一单时把六家报价记下来，与账面实扣核对。

## 7. 拒单（新增能力，方案里原本没有）

**入口在详情抽屉底部**，红色文字链接，不在卡片上——拒单低频但要退款，放卡片上容易误点。

流程：

1. **必须选原因**，未选时确认按钮禁用。五个选项（**顾客会原样看到这几个字**）：

   | 选项 | 备注 |
   |---|---|
   | 菜品售罄 | 选中后展开菜品勾选，见第 2 条 |
   | 超出配送范围 | |
   | 已过接单时间 | 不用「快打烊了」——听起来是规则而非敷衍 |
   | 顾客电话要求取消 | |
   | 其他原因 | 选中后**强制填一句说明**（≤40 字），不填不让提交 |

2. **选「菜品售罄」时展开该单菜品勾选，勾中的确认后自动下架。**
   这一步是关键联动：不下架的话下一位顾客照样点得到，同样的单会再来一遍，等于白拒。

3. 红色警示条写明金额：`确认后全额退款 ¥69.00 原路退回，顾客会收到退款通知。此操作不可撤销。`

4. 确认后：全额退款（走现有 `initiateRefund`）+ 订单终态 **`REFUNDED`** + 拒单原因写入 `cancelReason` + 勾中的菜品置 `OFF_SHELF`。

**终态是 `REFUNDED` 不是 `CANCELLED`**（店主 2026-09-04 确认，此前 §7 留的是早期草稿措辞）。
理由有两层：技术上，拒单本来就要走 `initiateRefund` 全额退，让它自然走完退款流程落在 REFUNDED，
退款的幂等与对账都不用动；强行改写成 CANCELLED 等于在退款流程之外再插一次状态覆写，退款回调回来时会对不上。
顾客角度上，被拒单时他最关心的是「钱回来没有」，「已取消」不回答这个问题。

**顾客端文案两行**——拒单事实与退款事实都要说到：

```
商家已拒单 · 菜品售罄
款项 ¥69.00 已原路退回
```

第二行随退款单的**实时状态**变（`PENDING`/`PROCESSING` 写「退款处理中」，`SUCCESS` 才写「已原路退回」），
所以由顾客端按 `refunds[0].status` + `refundedAmount` 渲染，**服务端不拼死这个字符串**：
同一个 `cancelReason` 还被后台订单列表与退款订阅消息消费，在服务端改写它的格式会同时污染那两处。

**服务端需要新增**：`POST /admin/local/orders/:id/reject { reason, note?, soldOutProductIds?: number[] }`
在一个事务里完成退款发起、订单流转、商品下架；有在途配送单时先按 42221 拦下（要求先取消配送单）。

## 8. 顶栏

左：店名 + 日期 · 营业状态 · 打印机状态 · 待处理告警数
右：今日单数 / 营业额 / 平均送达时长 · **日夜切换** · **全屏** · **退出工作台**

- **日夜切换**：默认跟随系统（不写 `data-theme`），点击后写 `data-theme` 并存 localStorage（`try/catch` 包住）。
- **全屏**：`requestFullscreen()`；被浏览器/iframe 拒绝时退化为「专注模式」——隐藏图例与说明，屏幕全给看板。两条路径都要有。
> 手机（≤700px）上顶栏只留前四项，统计与三个按钮收进「⋯」，见 §9.1。

- **退出工作台**：确认框必须写明 **「工作台仍在后台接单、出票和播报，退出不影响来单提醒」**，否则店员不敢退。

## 9. 响应式

三档，界线按设备形态分，不按好看的整数分：

| 宽度 | 形态 |
|---|---|
| ≥ 901px | 电脑 / iPad 横屏：四列并排 + 「已完成」折成 44px 竖条，列内各自滚动 |
| 701–900px | iPad 竖屏：五列横向滑动、一屏一列（`grid-auto-columns:86vw`），页面整体滚动 |
| ≤ 700px | **手机模式**，见 §9.1 |

700 这条线是为了把 iPad 排除在外：iPad mini 竖屏 744、iPad 竖屏 768 / 810 / 834 都落在中间那档，
手机竖屏最宽约 440 落在手机档。**店主 2026-09-07 定：这一轮只改手机，电脑与 iPad 的构造一行不动。**

### 9.1 手机模式（≤ 700px）

改造前在 375×812 实测：顶栏 169px + 图例 147px = **316px，占首屏 39%**，首屏只看得见 3 张卡片；
列内滚动被关掉后整页高 **18,592px**（待接单 120 张），想横滑换列得先纵向滚回顶部；
「已完成」那一列被 `86vw` 撑成整屏宽，横滑时白划过一屏空白。

手机模式按「一次一列 + 吸顶切换」重排：

**顶栏**（169 → 48px）：只留店名、营业状态点、打印机灯、待处理告警数。
今日单数 / 营业额 / 平均送达、日夜切换、全屏、退出工作台收进右侧「⋯」。
全屏在小程序 web-view 里本来就调不起来，放在一级位置是浪费。

**列切换条**（新增 44px，吸顶）：五个列名横向排开、各带条数角标，点一下换列，默认停在「待接单」。
这是手机上换列的**主**方式——页面高 18,000px 时「横滑找列」根本用不了。

**看板**：一次只渲染当前列；卡片占满宽（不再留 86vw 那条下一列的边）；列内独立滚动，
`.wb` 用 `100dvh` 定高。**不能用 `100vh`**——地址栏收放会跳，上一版正是因此把列内滚动
整个关掉改成整页滚，才有了 18,592px 那个数。列头不再单独占一行，列名与条数已在切换条上。

**图例与底部阈值说明**：合成顶栏上的一个「?」，点开是半屏说明层，内容一字不改。
§3 的三重编码指的是**卡片上**的色条 + 徽章 + 字段差异，那三样一个不少；
图例是解释这套编码的说明——新店员前几天需要，之后每天占 147px 不值。

**详情抽屉**：仍是全屏（`width:100vw`），本轮不动。

> 实现约束：CSS 的 `@media (max-width:700px)` 与 JS 的 `useIsPhone` 必须用**逐字相同**的查询串。
> 两边对不上会出现「手机 DOM 套桌面样式」——那比两端都不改还糟。

## 10. v1 明确不做

### 一对一 / 指定单家运力 —— 留口子，界面不做

店主 2026-09-03 决定：**v1 不引入「一对一专送」这个概念**，呼叫骑手就是按设置里的运力列表并呼。
后续如果要加（例如接入顺丰同城后，做成「并呼六家 / 顺丰同城一对一」二选一），
希望**只改配置、不动接口结构**。因此实现时预留：

- 呼叫接口签名用 `providers?: string[]`（覆盖设置里的默认列表），**不要做成 `oneToOne: boolean`**。
  布尔值把「哪家算一对一」焊死在代码里；具名列表将来换成闪送或别家时，接口和数据结构都不用动。
- `Delivery` 表记录本单**实际呼了哪些运力**，将来对账才看得出费用差异来自哪里。
- 设置里可预留 `kd100.soloProvider`，v1 不在界面上暴露。

> 背景：凉菜是体积大于重量的品类——一份打包盒约 1.5 L，15 份就 20 多升，
> 而外卖电动车保温箱常见 40–60 L。所以大单装不下的真正原因是**骑手已接了别家的单**（拼单），
> 不是超重。这也是为什么解法是「指定不拼单的运力」而不是「限制重量」。
> 另：顺丰同城通过快递100 下单是否真的不拼单，尚未向快递100 确认，所以更不能写死。

### 其他不做

- 列的拖拽排序、自定义列
- 历史订单检索（留在 `/local/orders` 列表页）
