# 生产库测试单的标记与清理

快递100 出票联调、小程序上线前回归，都要在**生产服务器、正式库**上跑，会留下几笔真实的测试订单。
店刚起步，数据本来就少，几笔测试单在趋势图上会顶出假峰，累积几轮下来早期数据就不能看了。

这份说明只讲一件事：**怎么让测试单不进经营统计，怎么让它不污染销量。**
这是两条互不重叠的机制，缺一不可。

| 污染什么 | 隔离手段 | 为什么 |
| --- | --- | --- |
| 订单数、营业额、趋势图 | 订单打 `isTest` 标记 | 统计都是实时查订单表，加一个共用 where 就全挡住 |
| 扫码转化率 | **只挡住一半** | 分子（订单数）排除了测试单，但分母（扫码次数）来自 `scan_logs`，那张表没有测试标记。联调账号若在同一区间既扫过码又下过测试单，转化率会**偏低**。要彻底干净得连扫码侧一起标（`ScanLog` 已有 `source` 字段），留待需要时再做 |
| 商品「已售 N 份」、后台热销榜 | 用专门的测试商品，联调后软删除 | 销量是商品上的冗余列，跟订单行无关，`isTest` 挡不住（见下节） |
| 后台「优惠券」页多出几张测试模板 | 测试券模板联调后**停用**（不是删除） | 券模板没有删除操作——删了已发券的 `template_id` 就悬空。停用只挡再发放 |
| 顾客结算页多出一件测试赠品 | 测试赠品联调后**删除** | 赠品配置可以删（`order_items` 落的是快照，不引用它的 id），删掉顾客侧立刻看不见 |
| 联调账号的积分与券余额 | **不清理** | 已发出去的东西不追改，是这套账的设计取向（见 `docs/database.md` 3.9）。把券码记进联调记录即可 |

---

## 一、联调前：建一个专门的测试商品

在后台新建一个只给联调用的商品：

- 名字带明显前缀，例如 `【内部联调】测试商品`，价格取能覆盖起送门槛的最小值（同城联调需要真实下单付款）。
- 分类选对渠道（同城联调放同城分类，出票联调放邮寄分类），否则下单时渠道校验会拦。
- 库存给够跑完几轮的量。

**联调全程只买这一个商品。** 不要拿真实在售商品下测试单——一旦买了，那个商品的「已售 N 份」
就永久多出几份，顾客在小程序商品页上直接看得到，而且改不回来。

## 二、联调后（第一步）：软删除测试商品

联调跑完，在后台把测试商品删掉（后台的删除是软删除，写 `deleted_at`，历史订单不受影响）。

删掉之后：

- 小程序前台看不到它，顾客不会看到那个被污染的「已售 N 份」；
- 后台热销榜按 `deleted_at IS NULL` 过滤，它也不再上榜。

销量污染就这样被关在一个已删除的商品里，不再外溢。

## 三、联调后（第二步）：把测试单标成测试单

对每一笔联调订单调一次（`<ORDER_ID>` 是后台订单详情里的数字 id，不是订单号）：

```bash
curl -X PATCH "https://<你的域名>/api/admin/orders/<ORDER_ID>/test-flag" \
  -H "Authorization: Bearer <管理员 token>" \
  -H 'Content-Type: application/json' \
  -d '{"isTest": true}'
```

标错了可以撤销，把 `true` 换成 `false` 再调一次即可。

关于这个接口：

- 没有界面，故意的——它是低频的运维动作，不是日常操作，不该出现在店员点得到的地方。
- **没有「仅非生产环境」守卫**，因为联调恰恰发生在生产环境，挡掉就等于这功能不存在。
  鉴权与其它后台写接口同级（管理员 token）。
- 它只改一个布尔，不退款、不改状态、不动库存、不碰销量。
- 每次变更都会发一条系统告警并写一行服务端日志（谁、什么时候、把哪张单标成了什么），
  因为这是会改变经营数据的操作，必须能追溯。

> **打标之前先把要打的单逐笔列出来。** 这是生产的经营记录，
> 「这批都是测试的」这句话对不对，得看清了才知道。2026-09-06 打历史遗留的 14 笔时
> 就是先列了一遍（付过款 11 笔 / 未付款 3 笔），顺手发现单1 状态 `REFUNDED` 却
> `refunded_amount=0` 这条不自洽的老数据——批量改是不会发现它的。

## 三点五、会员联调多出来的两类测试数据

会员功能（券与积分）联调还会留下**测试券模板**和**测试赠品**。两者的处理方式不一样，
原因也不一样，不要凭直觉统一处理。

### 建的时候

- 券模板名带 `【内部联调】`，面额取最小可验值（满 0 减 0.01）。三种来源各建一张才能覆盖全部路径：
  `ADMIN`（店员定向发放）、`POINTS`（积分兑换）、`CAMPAIGN`（领券中心，总量给 2 才验得到「已领完」）。
- 赠品指向**测试商品**（不要指向真实在售商品——赠品会扣真实库存），积分价给 1，每单限 1。
- **记下全部 id**：联调记录里要有，收尾时按 id 处理，不靠名字搜。

### 收尾的时候

| 对象 | 怎么处理 | 为什么不是别的做法 |
|---|---|---|
| 测试券模板 | 后台「优惠券」页点**停用** | 系统里**没有**删除券模板这个操作。删了会让已发券的 `template_id` 悬空、发放记录查不出来源。停用只挡再发放，已发的照常能用 |
| 测试赠品 | 后台「积分赠品」页点**删除** | 可以删。`order_items` 落的是商品与积分价的快照、不引用 `points_goods.id`，历史订单照常显示 |
| 联调账号手里剩下的测试券 | **不动** | 已发出去的券不回收，是设计取向而不是偷懒。把券码列进联调记录，将来客服对得上就行 |
| 联调账号的积分余额 | **不动**（同上） | 要归零只能靠等它过期。硬改会让 `points_balance` 与账本失步，`check-points-consistency.mjs` 会当场报错 |

### 顺序有个坑

**测试单的 `isTest` 标记必须在验完「得分」与「退款扣回」之后再打。**
`isTest` 的单不发积分（spec §5.4），打早了那两步永远验不到——不是不发，是根本不触发。

停用测试券模板时如果弹出「这张券正被设为**新客券**」，说明会员设置里选中了它：
先去「会员设置」改选别的模板或改成「不发新客券」，再停用。否则新注册的顾客会一张券都收不到，
而这件事在券模板页上是看不见的。

## 四、标记之后统计会怎么变（重要）

统计是**实时查询**，不是每日快照。所以把一张已经计入过统计的单标成测试单，
**历史数字会跟着回溯性变小**：趋势图上联调那天的柱子会矮下去，总订单数会减一，
当天营业额会减掉那笔实付金额。

这正是我们要的效果——联调造出来的假峰本来就该消失。但要知道它会变：
昨天截图里的数字和今天再打开可能对不上，那不是 bug。取消标记后数字会原样回来。

## 五、口径接在哪儿（给后来改代码的人）

共用条件定义在 `apps/server/src/utils/stats-scope.ts`：

- Prisma 查询：`where: { ...REAL_ORDERS, ... }`
- 原生 SQL：把 `${realOrdersSql('o')}` 拼在 WHERE 后面（参数是 orders 表的别名，没有别名就不传）

**新增任何统计查询都必须 spread 它，不要在各处手写 `isTest: false`。** 手写的问题不是麻烦，
是漏掉时完全静默——数字看着正常，只是偷偷多算了几笔测试单，没人会发现。

当前接入点（9 处，另有 2 处这个口径够不到，见下）：

- `routes/admin/stats.ts`：总订单数、今日订单数、今日销售额、近 7/30 天趋势（原生 SQL）
- `routes/admin/workbench.ts`：今日单数、今日营业额、平均送达时长
- `routes/admin/scan-stats.ts`：扫码转化订单数、按商品的转化（均为原生 SQL）

故意**没有**接的地方：

- **后台概览热销榜**（`stats.ts`）读 `Product.salesCount`，加多少 where 都过滤不掉，靠上面第一、二节隔离。
- **工作台的五列卡片**（`workbench.ts`）不排除测试单：联调时店员要在工作台上看着自己造的那一单
  走完流程。那是操作视图，不是统计。

## 六、为什么销量必须靠测试商品，而不能靠 `isTest`

`Product.salesCount` 是**下单那一瞬间就 +1** 的冗余列，它记的是「卖出去多少份」，
不回头看订单表，所以订单上标什么都影响不了它。

而这个 +1 只在订单停在**待付款 / 待接单 / 备餐中**时退款才会自动回滚
（见 `utils/order-stock.ts` 的库存与销量回滚）。测试单偏偏要跑完整流程到
**配送中 / 已完成**才能验证出票和配送——到了那一步再退款，这个 +1 就永久留下了。

而顾客在小程序商品页上**直接看得到**「已售 N 份」。所以：测试商品是唯一可靠的隔离手段，
软删除是唯一可靠的清理手段。

> 不要为了清销量去手改 `sales_count`。那列的记账逻辑是另一个话题，手改会让它和订单表更对不上。
