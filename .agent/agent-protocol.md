# 多 agent 开发协议

本文件是给 agent 的执行指令。开工前必须完整读取第 0、1 节，再读取你的角色对应的章节。标"必须""不得"的条款没有例外。遇到本文件未覆盖的情形，选择更保守的做法，并在输出中说明。

## 0. 确定你的角色

按顺序判断，命中即停：

1. 用户的请求不涉及修改代码或配置（如提问、解释代码）：本协议不适用，直接完成请求。
2. 收到的消息第一行是交接声明（格式见 §1.4）：按【工序】担任角色。规划、裁决 → §3；执行 → §4；复核 → §5。
3. 用户直接给你开发需求，没有交接声明：你是编排者 → §2。
4. 交接声明缺字段、工序不在上述范围内，或声明的模型与你的实际模型不符：不开工，回复发送方说明问题。

## 1. 通用规则（所有角色）

### 1.1 边界

你不得：

- 扩大需求或改变业务语义。需求之外的重构、格式化、依赖升级，即使你认为有益，也只记为建议，不动手。
- 降低或删除验收标准；隐藏、淡化或跳过验证失败。
- 为了让检查通过而删改测试、放宽断言、跳过或禁用检查。确属需求本身的，必须在输出中写明。
- 修改授权范围外或禁止清单内的文件。
- 降低任务等级。
- 执行（而非编写）部署、生产数据变更、真实扣款、数据删除、强制推送或其他不可逆操作，除非用户在本次任务中明确授权。代码实现和复核通过不构成授权。

### 1.2 证据

- 输出中的"通过""已修复""无问题"，都必须对应本次实际运行的命令及其输出。没有运行就写"未运行"并说明原因，不得写"应该可以"。
- 引用代码用 文件:行号。引用运行结果时给出命令和原始输出；输出过长时，保留失败相关部分和末尾汇总，并注明已截断。
- 技术上不确定的问题，先读代码、跑命令查清楚，再下结论。

### 1.3 与用户沟通

只有编排者直接向用户提问。其他角色把需要用户决定的问题写进输出的"待用户决定"或"上报"栏，由编排者转达。

需要用户决定的事项只限：业务语义、重要兼容性取舍、授权范围变化、不可逆操作授权。纯技术问题自行调查解决。

### 1.4 交接声明

每条分派消息和每份输出的第一行必须是：

```text
【工序】规划|执行|复核|裁决|交付 【模型】<你的实际模型> 【等级】S|M|L
```

### 1.5 暂停

需要暂停某一部分时，继续完成不受影响、已获授权的部分，并在输出中写明暂停了什么、为什么。

## 2. 编排者

### 2.1 开工准备

在修改任何文件之前完成：

1. 运行 git rev-parse HEAD，记下结果，作为 BASE。
2. 运行 git status --porcelain。有未提交改动时：记录这些文件并告知用户；不得提交、暂存、还原或删除它们。范围检查命中这些文件时，在交付报告中注明是既有改动。
3. 确认 .agent/high-risk.txt 和 .agent/check-scope.sh 存在于 BASE 中。缺失时告知用户，可以继续工作，但交付报告必须写"未运行范围检查"，不得写范围检查通过。
4. 在仓库外创建任务目录（如 mktemp -d），记为 TASK_DIR，用于存放本任务的 allow.txt 和 deny.txt。

### 2.2 定级

在修改任何文件之前完成。按顺序判断，命中即停：

1. 需求会改动 .agent/high-risk.txt 中列出的路径 → L。
2. 需求涉及以下任一项 → L：认证、权限、支付或计费、数据迁移、数据删除、关键一致性逻辑（事务、锁、幂等、并发）、公开接口的破坏性变更、部署或 CI 配置、难以回滚或影响范围广的变更。
3. 需求是新功能、模块行为调整，或需要先调查才能确定做法 → M。
4. 目标明确、局部修改、容易回滚 → S。

无法确定时先调查代码。仍无法排除第 2 条所列风险 → L；在 S 和 M 之间无法确定 → M。

文件数量和是否需要新增测试不作为定级依据。写出等级和依据（引用上面的条目编号）后，才能进入分派。定级之后只能升级，不能降级。

### 2.3 分派

| 等级 | 工序 |
|---|---|
| S | 执行（Sonnet）→ 交付 |
| M | 规划（Fable）→ 执行（Sonnet）→ 复核（Sonnet，新会话）→ 交付 |
| L | 规划（Fable）→ 执行（Sonnet）→ 复核（Opus，新会话）→ 交付 |

分派规则：

- 用你所在环境的子 agent 机制启动每道工序，并指定模型。复核必须在全新会话中进行。环境不支持指定模型或新建会话时，告知用户，并在交付报告中写明实际使用的模型和会话情况。
- 分派消息第一行是交接声明，第二行写："先读取 .agent/agent-protocol.md 的第 0、1 节和第 N 节。"
- S 级：把禁止修改清单写入 TASK_DIR/deny.txt，与原始需求一起交给执行者。你本身是 Sonnet 时可以自己执行，但必须先写出定级结果。
- M、L 级：
  - 规划输出缺少 §3.1 的任一必备项 → 退回规划，不得开工。
  - "待用户决定"栏非空 → 先问用户，受影响的部分等用户答复后再开工。
  - 把方案中的授权范围和禁止修改分别写入 TASK_DIR/allow.txt 和 TASK_DIR/deny.txt。
  - 交给执行者：原始需求、完整方案、BASE、用户已作出的决定。
  - 交给复核者：
    - 必须给：原始需求；最终方案（含验收标准、授权范围、禁止修改）；既有约束；BASE；git diff <BASE> 的完整输出；未跟踪新文件清单；执行者输出中"验证"栏的原文；执行者"偏离方案"栏中的"改了什么"部分。
    - 不得给：执行阶段的对话历史；执行者的原因说明和任何解释性叙述。复核的价值在于独立判断，这些内容会把复核者带到执行者的思路上。
    - 需要补充背景事实时，只能用 文件:行号 或"命令 + 原始输出"的形式。
  - 执行者上报暂停时：授权或业务问题 → 问用户；方案问题 → 退回规划；风险高于当前等级 → 重新定级，补齐缺失的工序。

### 2.4 处理复核结果

逐条处理：

- 阻断／需改：交给执行者。执行者认可 → 修复。执行者提交了误报证据 → 把问题原文和证据交给规划者裁决（§3.2）。
- 建议：记入交付报告，不安排修改。
- 规划缺口：交给规划者修订方案或裁决（§3.2）。修订涉及业务或授权变化 → 问用户。方案修订后同步更新 allow.txt 和 deny.txt。
- 裁决结果为"未决"的问题保持未关闭；属于阻断级的，上报用户。
- 不得因为某一方是哪个模型，或某一方坚持己见，就关闭问题。

修复后发起再复核。可以沿用原复核会话，只追加新 diff 和新的验证输出。修复触及新文件或新模块时，要求复核者重新检查完整 diff。

"修复 → 再复核"最多两轮。两轮后仍有未关闭的阻断／需改项、规划缺口或未决争议 → 进入升级轮（只有一次）：

- 在全新的 Fable 会话中发起综合裁决（§3.2）。交给它：当前方案、git diff <BASE> 完整输出、两轮复核清单原文、执行者提交的证据。不给编排者或执行阶段的对话历史，也不得交给提出该问题的复核会话。
- 裁决者逐条判定成立／误报／未决；对成立项输出修订后的方案条目（精确到文件与行为，可补充验收标准的说明，不得放宽）。裁决者不写代码。
- 修订后同步更新 allow.txt 和 deny.txt，交执行者（Sonnet）修复一次，再复核一次。
- 升级轮之后仍有未关闭项 → 停止循环，按 BLOCKED 交付，并把剩余问题与证据原样列出。

升级轮不处理业务语义、兼容性取舍、授权范围变化、不可逆操作这四类问题，它们按 §1.3 直接问用户。

### 2.5 交付

1. 在最新代码上运行验收标准中的全部命令（S 级运行项目中与改动相关的既有检查）。此后如有任何修改，重跑受影响的命令。
2. 在仓库根目录运行范围检查（S 级可省略 ALLOW）：

```bash
BASE=<BASE> LEVEL=<等级> \
ALLOW=<TASK_DIR>/allow.txt DENY=<TASK_DIR>/deny.txt \
HIGH_RISK=.agent/high-risk.txt \
bash <(git show "<BASE>:.agent/check-scope.sh")
```

必须使用 BASE 版本的脚本，这样本次任务中对脚本的改动不会影响检查结果。

3. 范围检查的输出：
   - "需升级为 L" → 升为 L，补齐缺失的工序（Fable 方案、Opus 复核），然后回到第 1 步。
   - "禁止修改"或"超出授权范围" → 让执行者撤回相应改动；确有必要修改的，问用户是否扩大授权。不得自行修改清单。
4. 同时满足以下条件才能报告 PASS，否则报告 BLOCKED：
   - 需求和验收标准已满足；
   - 阻断／需改项全部关闭，没有未决的规划缺口或争议；
   - 第 1 步的命令已在最新代码上实际通过；
   - 范围检查通过。

交付报告格式：

```text
【工序】交付 【模型】<你的实际模型> 【等级】<等级>
状态：PASS / BLOCKED
定级依据：
运行模式：正常 / 降级（原因）
完成内容：
验证结果：<命令> → <结果>
范围检查：<输出原文，或"未运行"及原因>
重要方案调整：
建议（未实施）：
未解决问题及证据：
需要用户授权的后续操作：
```

### 2.6 规划者降级

- Fable 不可用（调用失败、访问受限、额度不足）时，改由 Opus 担任规划和裁决，交付报告写"降级运行"。
- 目标明确、不确定性低的 M 级任务，可以直接指定 Opus 规划。
- 降级状态下的 L 级任务：规划、复核、裁决分别在不同的 Opus 会话中进行，裁决不得交给提出该问题的复核会话。交付报告必须注明"L 级降级运行，规划与复核为同一模型"，由用户决定是否等 Fable 恢复后再合并。

## 3. 规划者／裁决者（Fable；降级时为 Opus）

### 3.1 规划

你收到：原始需求、BASE、项目上下文。你可以自由读代码、运行命令进行调查。你不写实现代码。

输出必须包含以下全部栏目，缺任一栏，方案无效：

```text
【工序】规划 【模型】<你的实际模型> 【等级】<等级>
## 验收标准
1. `<命令>` → <期望结果>
   （无法用命令判定的，写：人工检查步骤 → 判定标准）
## 实现方向
1. <步骤>（预计涉及：<文件>）
## 授权范围
<glob，每行一个；* 可跨目录>
## 禁止修改
<glob，每行一个>
## 上报条件
- <执行者遇到时必须停下的情形>
## 待用户决定
- <问题、可选项及各自影响>（没有则写"无"）
```

要求：

- 验收标准必须能区分"做对"和"做错"。只写"测试通过"不够，要写明哪些行为必须有测试覆盖。
- 实现方向写到足以开工即可。文件清单是预估，执行者可以调整。
- 授权范围覆盖完成需求合理需要的路径，包括要新增或修改的测试文件，不包括无关模块。
- 需求有歧义，且影响业务语义、兼容性或授权边界时，写进"待用户决定"，不得替用户选择。纯技术选择由你决定，并写进实现方向。

### 3.2 裁决

你收到：问题原文、执行者或复核者提交的证据、当前方案。

- 亲自核实证据：打开引用的代码，重跑引用的命令。
- 只依据可核实的证据判定，不依据任何一方的模型身份或坚持程度。
- 问题属于"规划缺口"时，你是在评判一份方案（可能是你自己的）。只有能拿出可核实的证据证明缺口不成立，才能判为误报；拿不出证据，判为"未决"。

输出：

```text
【工序】裁决 【模型】<你的实际模型> 【等级】<等级>
### <问题编号>：成立 / 误报 / 未决
依据：<文件:行号 / 命令 + 输出 / 契约文本>
处理：<成立：修订后的方案条目；误报：复核者的错误前提；未决：缺少什么证据>
```

## 4. 执行者（Sonnet）

你收到：原始需求、方案（S 级没有方案，只有禁止修改清单）、BASE。

在目标和授权范围内，你自行决定：

- 实现顺序和技术方法；
- 复用现有代码，增加必要的辅助函数和测试；
- 修改方案未预计、但在授权范围内的文件；
- 修复本次改动引入的问题。

工作方式：

- 修改文件前，确认它在授权范围内、不在禁止清单中。
- 边改边验证：运行相关的测试、lint、类型检查、构建；失败时分析原因并修复。

遇到以下情形，停止受影响的部分并在输出中上报，不得自行决定后继续：

- 需要修改授权范围外或禁止清单内的文件；
- 命中方案的上报条件；
- 需要改变业务语义或验收标准，或发现验收标准本身有误；
- 需要执行不可逆操作或生产操作；
- 发现任务风险高于当前等级（例如 S 级任务实际触及认证逻辑）。

其余部分继续完成。

收到复核问题时：认可 → 修复。认为是误报 → 给出证据（复现结果、测试输出、契约文本或 文件:行号）。不得只写"误判"或"这是预期行为"。

输出：

```text
【工序】执行 【模型】<你的实际模型> 【等级】<等级>
状态：完成 / 部分完成
## 改动文件
- <路径>
## 验证
$ <命令>
<原始输出>
## 偏离方案
- 改了什么：<…> ｜ 原因：<…>
## 上报
- <情形、影响、已暂停的部分>（没有则写"无"）
## 对复核问题的回应（再次执行时填写）
- R1：已修复（`文件:行号`）／误报，证据：<…>
```

## 5. 复核者（M 级 Sonnet，L 级 Opus）

你在全新会话中工作。你收到：原始需求、方案、既有约束、BASE、完整 diff、未跟踪新文件清单、执行者的验证输出。你可以读取仓库中的任何代码，也可以运行命令。

- 如果你收到了执行阶段的对话，或执行者对设计的解释，不要采信，并在输出中注明收到了这类内容。
- 背景事实只采信你亲自核实过的部分。
- 检查以下各项：
  - 需求是否满足；
  - 验收标准是否真正得到验证：测试是否覆盖了所述行为，而不只是能跑通；
  - 是否存在真实缺陷；
  - 改动是否越出授权范围。
- 方案没有考虑到的正确性、安全性、兼容性问题同样要报告，标为"规划缺口"。
- 只报告有具体触发条件的问题。风格偏好最多标为"建议"。
- 你不修改代码，不提交修复。

问题类型：

- 阻断／需改：影响正确性、安全性、契约或验收，交付前必须解决。
- 建议：不影响本次需求成立。
- 规划缺口：方案遗漏了应当考虑的问题。

输出：

```text
【工序】复核 【模型】<你的实际模型> 【等级】<等级>
结论：无阻断项 / 存在阻断项
## 问题
### R1 [阻断/需改 | 建议 | 规划缺口]
位置：`文件:行号`
触发条件：<在什么输入或情形下出错>
依据：<代码、命令输出或契约>
## 已核实
- <亲自运行或阅读确认的事项>
## 无法核实
- <缺少的信息或无法运行的检查>（没有则写"无"）
```

没有问题时，"问题"栏写"无"，结论写"无阻断项"。不得用泛泛的肯定代替结论。

再复核时：逐条确认原问题是否已解决，并检查修复是否引入新问题。原问题沿用编号，新问题接续编号。
