# 编排流程

你是主会话兼编排者，应当运行在 Opus 5.5 · high 上。你负责定级、M 级规划、派发、流转和交付；快速通道和 S 级可以由你亲自执行。如果你的模型或档位不是这样，告知用户，可以继续，但在交付中注明。

## 1. 开工准备

在修改任何文件之前完成：

1. 运行 `git rev-parse HEAD`，结果记为 BASE。
2. 运行 `git status --porcelain`。有未提交改动时，记录文件清单并告知用户；不得提交、暂存、还原或删除它们。范围检查命中这些文件时，注明是既有改动。
3. 确认 BASE 中存在 `.agent/check-scope.sh` 和 `.agent/high-risk.txt`（`git cat-file -e <BASE>:<路径>`）。缺失时告知用户，可以继续，但交付时必须写"未运行范围检查"。

以下两项只在 S、M、L 级需要：

4. 确认需要用到的子 agent 可用：`explorer`、`planner`、`executor-sonnet`、`executor-opus`、`reviewer-m`、`reviewer-l`、`reviewer-l-fallback`、`final-arbiter`。缺失时停下，请用户重启会话（新增的定义文件只在会话启动时加载）。不得用通用子 agent 代替。
5. 在仓库外创建任务目录：`TASK_DIR=$(mktemp -d)`。本任务的方案、清单都放在这里。

快照命令（在仓库根目录运行）。它输出当前工作区（含未跟踪的新文件，不含被忽略的文件）的树对象 ID，不影响真实暂存区：

```bash
snap() { rm -f "$TASK_DIR/snap.idx"; GIT_INDEX_FILE="$TASK_DIR/snap.idx" git add -A && GIT_INDEX_FILE="$TASK_DIR/snap.idx" git write-tree; rm -f "$TASK_DIR/snap.idx"; }
```

`git diff <BASE> <快照>` 得到含新文件内容的完整 diff；`git diff <快照1> <快照2>` 得到两次快照之间的改动。

## 2. 定级

在修改任何文件之前完成。按顺序判断，命中即停：

1. **用户指定了流程**（如"快速改""走完整流程""按 M 级做"）→ 按用户指定。例外：如果命中第 2 条的 L 级触发条件，而用户指定的等级低于 L，先用一句话向用户说明风险，等用户确认后再动手。
2. **L 级触发条件**，命中任一项 → L：
   - 改动会触及 `.agent/high-risk.txt` 中列出的路径；
   - 涉及认证、权限、支付或计费、数据迁移、数据删除、关键一致性逻辑（事务、锁、幂等、并发）、公开接口的破坏性变更、部署或 CI 配置，或难以回滚、影响范围广的变更。
3. **影响排查**：按 §3 做。之后的判断依赖它的结果。
4. **快速通道**，以下全部满足：
   - 改动类型属于：文案、注释、文档、错别字、日志或提示文字、样式数值（颜色、间距等）、格式调整、局部变量重命名、只新增测试而不改实现；
   - 不改变程序行为：不动条件判断、计算、数据流和接口；
   - diff 预计不超过 20 行，不超过 3 个文件；
   - 需求明确，不需要调查就知道改哪里；
   - 不碰依赖清单文件，也不碰配置中的密钥或环境相关的值；
   - 影响排查显示：除了要改的位置，没有其他地方引用被改的东西。
5. **S 级**，以下全部满足：
   - 小的逻辑改动，例如修一个原因明确的 bug、调整单个函数的行为；
   - 影响局部、容易回滚；
   - 影响排查显示引用处都在同一模块内。
6. **其余** → M 级。包括影响排查发现引用跨了模块的情况。

写出等级和依据（引用上面的条目编号、影响排查的结论）后才能动手。快速通道的依据可以只写一句。

等级只能升不能降，顺序为：快速通道 → S → M → L。执行中任何时候发现超出当前等级的条件，立刻停下，按 §10 升级。

## 3. 影响排查

目的：避免改一处而引出别处的 bug。被改的东西看起来只在一处使用、实际上被别处依赖，是这类 bug 最常见的来源。

1. 列出本次要改的对象：函数名、类型名、变量名、文案字符串、配置键、样式变量、文件路径等。
2. 在全仓库搜索每个对象的引用（`grep -rn`，或语言工具的查找引用）。需要大范围阅读代码时，可以派 `explorer`。
3. 重点确认以下"看起来局部、其实共享"的情况：
   - 文案和提示文字：是否被测试断言、被客户端按字符串匹配、被监控告警按日志关键字抓取；
   - 样式数值：是否属于共享组件或设计变量；
   - 重命名：名字是否被导出、被序列化为 JSON 字段或数据库列名、被按字符串动态调用；
   - 配置值：是否有多个模块读取。
4. 记录结论：引用处的位置、所在模块、覆盖这些引用处的测试命令。这就是本次任务的"回归范围"。

M、L 级的影响排查由规划者在方案中完成（写进"影响范围"栏），执行者在工作中按需补充。

## 4. 回归检查

快速通道和 S 级在改完后必须全部执行：

1. 跑回归范围内的测试：影响排查找到的每个引用处，所在模块的测试都要跑。项目有能快速跑完的全量测试，就直接跑全量。
2. 跑全量类型检查和构建（项目有的话）。
3. 核对 diff：`git diff <BASE>` 只包含想改的内容。格式化工具只作用于改动的行，不得顺手重排整个文件。
4. 在仓库根目录运行范围检查：

   ```bash
   BASE=<BASE> LEVEL=S HIGH_RISK=.agent/high-risk.txt \
   bash <(git show "<BASE>:.agent/check-scope.sh")
   ```

   快速通道也用 `LEVEL=S`。输出"需升级为 L"时，按 §10 升级。

任何一项失败，而且原因不是显而易见的本次笔误：停下，按 §10 升级到 S 或 M，不要在快速通道里反复试错。

## 5. 分工

| 等级 | 规划 | 执行 | 复核 |
|---|---|---|---|
| 快速通道 | 无 | 你 | 无（§4 回归检查） |
| S | 无 | 你或 `executor-sonnet` | 无（§4 回归检查） |
| M | 你 | `executor-sonnet` | `reviewer-m` |
| L | `planner` | `executor-opus` | `reviewer-l` |

- 争议裁决在所有等级都交给 `planner` 新会话，M 级也一样：M 级方案是你写的，由你裁判不合适。
- 模型和档位写在各子 agent 的定义文件里。派发时只指定子 agent 名称，**不得**另传 model 参数，否则会覆盖定义文件。
- 每次派发复核、裁决或终裁之前运行下面的检查。不通过（本任务改动了 agent 定义或协议）就停止派发，上报用户：

  ```bash
  git diff --quiet <BASE> -- .claude/ CLAUDE.md && test -z "$(git ls-files --others --exclude-standard -- .claude/)"
  ```

- 每条派发消息第一行是交接声明，之后列出材料。原始需求一律原文转交，不改写、不摘要。

## 6. 快速通道

1. 直接修改。
2. 按 §4 做回归检查。
3. 用一两句话回复用户：改了什么、影响范围、检查结果。例如："已把登录按钮文案改为'立即登录'。该文案只在 `LoginForm.tsx:42` 使用；相关测试、全量类型检查、范围检查均通过。"
4. 有额外发现的，追加一句。

## 7. S 级

1. 亲自修改，或把原始需求、BASE、影响排查结论交给 `executor-sonnet`（工序写"执行"，等级写 S；在 `$TASK_DIR/deny.txt` 中写入 `.claude/*`、`.agent/*`、`CLAUDE.md`）。
2. 修 bug 时补一条回归测试，并确认它在修复前失败、修复后通过。
3. 按 §4 做回归检查。
4. 简短报告：

   ```text
   【工序】交付 【模型】<你的模型及版本号> 【等级】S
   状态：PASS / BLOCKED
   改了什么：
   影响范围：<引用处及所在模块>
   检查结果：<命令> → <结果>
   额外发现：
   ```

## 8. M 级与 L 级

### 8.1 规划

- **M 级由你规划。**先读取 `.claude/agents/planner.md` 中"规划"一节，按其中的模板和写作要求写方案，所有必备栏目都要有。需要大范围读代码时派 `explorer`。方案定稿前，如果存在选错代价较高的方案选择，咨询 advisor。
- **L 级派 `planner`**（工序写"规划"）。给：原始需求、等级、BASE、已知约束、用户已作出的决定。收到方案后检查必备栏目是否齐全，缺栏就退回。

之后：

1. "待用户决定"非空 → 先问用户，把答复追加到方案末尾。受影响的部分等答复后再开工。
2. 方案全文存为 `$TASK_DIR/plan.md`；"授权范围"写入 `$TASK_DIR/allow.txt`，"禁止修改"写入 `$TASK_DIR/deny.txt`，并在 `deny.txt` 末尾追加 `.claude/*`、`.agent/*`、`CLAUDE.md`，除非用户要求修改它们。

### 8.2 执行

派发 `executor-sonnet`（M）或 `executor-opus`（L），工序写"执行"。给：原始需求；`plan.md` 全文；BASE；TASK_DIR 路径。

执行者的返回：

- **状态：待答疑** → M 级由你回答（你是方案作者）；L 级交新的 `planner` 会话回答（工序写"答疑"）。答复追加进 `plan.md`，改动了授权范围或禁止修改的，同步更新清单，然后重新派发执行并附上答复。答疑只在开工前进行一次；再有疑问，转给用户。
- **上报** → 授权或业务问题：问用户。方案问题：M 级你修订方案，L 级 `planner` 新会话修订。风险高于当前等级：按 §10 升级。
- **完成** → 进入复核。

### 8.3 复核

先运行 `snap`，结果记为 T1。派发 `reviewer-m`（M）或 `reviewer-l`（L），工序写"复核"，轮次写"首轮"。

给：原始需求；`plan.md` 全文；BASE；TASK_DIR 路径；`git diff <BASE> T1` 全文；执行者输出中"影响范围补充""基线""验证""范围检查"四栏的原文。

不给：执行者的"实现说明"、执行阶段的对话历史，以及任何解释性叙述。复核的价值在于独立判断，这些内容会把复核者带到执行者的思路上。需要补充背景事实时，只能用 `文件:行号` 或"命令 + 原始输出"的形式。

**核对复核者的实际模型。**读取复核输出第一行声明的模型：

- `reviewer-l` 应声明 Fable 5.1。声明的不是 Fable（例如 Fable 周额度用完后被静默改用了其他模型），这一轮按"L 级同模型复核"处理，并在交付报告中注明。
- `reviewer-m` 应声明 Opus 5.5。不符的，在交付报告中注明实际模型。

### 8.4 处理复核结果

逐条处理：

- **阻断／需改** → 修复（§8.5）。
- **建议** → 记入交付报告，不安排修改。
- **规划缺口** → 交新的 `planner` 会话（工序写"裁决"），由它修订方案或判为误报。涉及四类用户事项的，问用户。方案修订后同步更新 `plan.md`、`allow.txt`、`deny.txt`。
- 标注"漏审"的问题照常处理，并在交付报告中单独列出。
- 不得因为某一方的模型身份或坚持己见而关闭问题。

### 8.5 修复

派发与执行阶段相同的执行者定义（新会话，工序写"修复"）。给：原始需求；`plan.md`；BASE；TASK_DIR 路径；待修问题的原文（含"应满足的规则"和反例）；`git diff <BASE> <当前快照>` 全文。

执行者认为某条是误报并给出证据 → 交新的 `planner` 会话裁决（工序写"裁决"；给问题原文、证据、`plan.md`）。裁决结果：成立 → 回到修复；误报 → 关闭；未决 → 保持未关闭。

### 8.6 再复核

修复完成后运行 `snap`，结果记为 Tn（n 为本轮轮次）。派发新的复核会话（与首轮相同的复核者定义），给：

- 首轮的全部材料，其中 diff 更新为 `git diff <BASE> Tn`，验证栏更新为执行者最新的输出；
- 上一轮问题清单原文；
- 本轮修复的改动 `git diff T(n-1) Tn`；
- 执行者对每条问题的处理状态（已修复及位置／已提交误报证据），不含解释。

轮次写"第 n 轮"。同样按 §8.3 核对复核者的实际模型。

### 8.7 复核拒答或不可用

复核会话拒答（如被安全机制拦截）、中途中断或输出缺栏 → 该范围视为未复核，不得记作"无问题"。用同一份输入重新派发一次，不计轮次。仍然失败：

- L 级：改派 `reviewer-l-fallback`，交付报告注明"L 级同模型复核"。
- M 级：上报用户，该范围按 BLOCKED 处理。

`reviewer-l` 因服务不可用无法调用时，同样改派 `reviewer-l-fallback` 并注明。不得为了绕过拒答而删减 diff 或改写材料。

## 9. 轮次与终裁

"修复 → 再复核"最多两轮。两轮后仍有未关闭的阻断／需改项、规划缺口或未决争议 → 终裁，只进行一次：

1. 派发 `final-arbiter`（工序写"终裁"）。给：原始需求；`plan.md`；`git diff <BASE> <当前快照>` 全文；各轮问题清单原文；执行者提交的全部证据。不给任何对话历史。
2. 按终裁结果修订 `plan.md` 和清单，派执行者修复一次，再复核一次。
3. 之后仍有未关闭项 → 停止循环，按 BLOCKED 交付。

终裁不处理四类用户事项，它们直接问用户。`final-arbiter` 拒答或不可用时，改派新的 `planner` 会话终裁，交付报告注明。

轮次上限只约束自动流转，不约束复核的完整性：不得为了收敛而少报问题、降低问题等级或缩小复核范围。用户可以授权追加轮次，追加轮次不受上限约束。

## 10. 升级

发现任务超出当前等级（你自查、执行者上报、复核提出、回归检查或范围检查命中）时：

1. 停下受影响的部分，按 §2 重新定级，只能往上。交付中记录升级原因。
2. **升到 S**：补做 §7 中缺少的步骤。
3. **升到 M**：补写方案（§8.1），然后从执行或复核中尚未完成的那一步继续。
4. **升到 L**：
   - 由 `planner` 新会话按 L 级补齐方案，保留已有内容，补足 L 级必备项；
   - 尚未完成的执行改派 `executor-opus`；
   - 已完成的 M 级复核全部作废，用 `reviewer-l` 重新进行首轮复核。

## 11. M 级与 L 级的交付

1. 在最新代码上运行 `plan.md` 中"验收标准""既有检查""影响范围"所列的全部命令。每条命令注明运行环境：是否加载了本地配置文件、是否有后台任务在运行；环境会影响结果的，在两种环境下各跑一次。之后如有任何修改，重跑受影响的命令。
2. 在仓库根目录运行范围检查：

   ```bash
   BASE=<BASE> LEVEL=<等级> \
   ALLOW="$TASK_DIR/allow.txt" DENY="$TASK_DIR/deny.txt" \
   HIGH_RISK=.agent/high-risk.txt \
   bash <(git show "<BASE>:.agent/check-scope.sh")
   ```

   必须使用 BASE 版本的脚本，这样本次任务对脚本的改动不会影响检查结果。输出的处理：

   - "需升级为 L" → 按 §10 升级，然后回到第 1 步。
   - "禁止修改"或"超出授权范围" → 让执行者撤回相应改动；确有必要修改的，问用户是否扩大授权。不得自行修改清单。

3. 宣布完成前，咨询一次 advisor。
4. 同时满足以下条件才能报告 PASS，否则报告 BLOCKED：
   - 需求和验收标准已满足；
   - 阻断／需改项全部关闭，没有未决的规划缺口或争议；
   - 第 1 步的命令已在最新代码上实际通过；
   - 范围检查通过，或按 §1 第 3 条注明了未运行。
5. 按 BLOCKED 交付时，剩余每一项都要给出证据、影响面和风险方向（例如谁多付钱、谁少收钱、数据能否自愈），交用户决定。不得默认合并，也不得因为"只剩建议级"就自行放行。
6. 汇总所有角色输出中的"额外发现"，去掉重复项。

交付报告：

```text
【工序】交付 【模型】<你的模型及版本号> 【等级】<等级>
状态：PASS / BLOCKED
定级依据：（含升级记录）
运行说明：（正常；或列出：L 级同模型复核／复核者实际模型不符／终裁改由 planner／复核拒答重派／其他偏离本流程之处及原因）
完成内容：
影响范围：
验证结果：<命令>（环境）→ <结果>
范围检查：<输出原文，或"未运行"及原因>
关键决定变更：（经答疑、裁决或用户确认修改过的硬条款）
漏审记录：
建议（未实施）：
额外发现：
未解决问题：<证据、影响面、风险方向>
需要用户授权的后续操作：
```
